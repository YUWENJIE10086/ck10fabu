三引擎升级 · 机理内核 + 机器学习增强

烤房智管算法融合升级方案：
机理内核保留 + LSTM 时序寿命预测 + 随机森林预警分类

本方案在不改动现有 健康分 / 剩余寿命 / 千亩村发展指数 三大机理内核的前提下，新增两层数据驱动引擎—— LSTM 长短时记忆 做寿命时序预测、随机森林 做预警分类。机理模型负责"可解释地算分"，机器学习负责"自动地学习规律与分类"， 二者互为表里，既保住了已落地的业务口径，又把项目的技术档次从"规则模型"提升到"深度学习 + 机器学习双引擎"。

第一步 现状盘点：现在用的三个"机理模型"，能做什么、缺什么

一句话现状 当前系统跑的三个算法都是 机理 / 规则驱动（公式+阈值+查表），可解释性强、绝不玄学，但"学习能力"为 0—— 它们是"算我们定好的公式"，不是"从数据里自己学到规律"。这既是优点（稳、可信），也是下一步升级的空间（缺"智能"）。

算法内核公式本质输出升级前缺什么
健康分 H H = 0.80·P_norm + 0.10·M + 0.10·E；
P_norm 逐部件 Cᵢ=Wᵢ·Lᵢ·Sᵢ / 有效权重		 机理/规则 0–100 分 + 五档健康等级 没有"趋势"，只看当前一个截面
剩余寿命 RUL R_b = 0.6·min_r + 0.4·R_avg；
RUL = clamp(R_b × (0.75+H/400))		 解析外推 剩余年限 + 四档预警 寿命靠"外推曲线"，不是"学出来的"
发展指数 V V = 0.50·Hc + 0.30·Lc + 0.20·Dc 加权指数 村级 0–100 + 新建需求分 N 村与村、部件间的复杂关联没被识别
这版方案要不要 LSTM / 随机森林？—— 诚实结论
  • 现状：完全没用。寿命不是时序预测，预警不是分类模型。这一点如实说明即可，不丢人，反而衬托出"升级有价值"。
  • 能加、影响小：我们只做"增强层"，坐在三个机理模型 输出之上 做特征与复核，核心公式与分数不变，既有页面与数据库结论不推翻。
  • 真能用：不必标榜"千万级数据"——2442 栋烤房 + 历年维修台账 + 逐部件指导寿命，足以重建每栋的年退化序列、训练分类器。小而真的模型，比空壳更抗评审追问。

第二步 总体架构：机理层（算）→ 特征层（喂数据）→ 学习层（LSTM+随机森林）→ 决策融合层（给结论）

核心设计一句话 "把三个现有机理模型的输出，当作机器学习引擎的特征和标签；机理模型是老师，机器学习是助手——机理保底、机器学习增强、决策融合把关。"
【第 0 层 · 机理内核（保留，可解释）】 健康分 H —— 已有 剩余寿命 RUL_基 —— 已有 发展指数 V —— 已有 【第 1 层 · 特征工程（从机理输出 + 台账构建）】 单栋特征向量 X_i = [H, RUL_基, 短板部件剩余, 风险缺口Top3, 近3年维修次数, 累计维修次数, 维修类型分布, 上次维修距今, 容量, 房龄, 覆盖材料, 加热器类型, 数据完整率] 村级特征向量 X_c = [V, Hc, Lc, Dc, 承载压力P, 新建需求N, 面积趋势] 【第 2 层 · 学习引擎（新增，数据驱动）】 引擎A LSTM 寿命时序预测 —— 输入退化时间序列 → 输出 RUL_lstm 引擎B 随机森林预警分类 —— 输入特征向量 → 输出 预警等级 + 概率 + 特征重要性 【第 3 层 · 决策融合（把关，可解释）】 RUL_final = α·RUL_lstm + (1−α)·RUL_基 （α建议 0.35） 预警等级 = 随机森林主分类，机理阈值复核；不一致 → 标记"人工复核"

关键：第 0 层 永远不缺席。机器学习只是加减法外的一层"经验加权"，即便模型再差，机理结果仍兜底输出，系统不会崩。

关键 如何与现有三个算法"扯上钩"：机理输出当特征、历史台账当时序

这是评审最可能追问的一句——"你说的机器学习，跟你们已有的三个算法到底什么关系？" 答案分三点：

1) 健康分 → LSTM 的"退化时序原料"

健康分目前是单一截面（只算当前 H）。我们把它按年份回放：用"建成年 + 逐年 CDCI 退化 + 维修台账回春"重建每栋 1980→2026 的健康分时间序列 H(t)。这条序列就是 LSTM 的输入。

2) 寿命/健康 → 随机森林的"标签与特征"

用现有 RUL 规则生成训练标签（正常/需关注/建议维修/紧急维修四档），用 H、RUL、部件风险缺口、维修统计当特征。随机森林学到的本质是"什么特征组合会导致哪档预警"。机理模型是老师的答案。

3) 发展指数 → 村级预警/选址的"上下文"

V、Hc、承载压力 P、新建需求 N 进入随机森林村级特征，让"该不该重点管某村 + 高压村预警"带上村级视角，而不是只看单栋孤例。

给评委的一句话（怎么"扯上钩"）

"我们的三个机理算法负责把业务逻辑算得清清楚楚，LSTM 和随机森林负责再从这些数里学出规律、自动分类、提前预警——机理是'规定动作'，机器学习是'自我进化'，两套引擎共享同一份台账，口径完全一致，互为印证。"

引擎 A LSTM 时序寿命预测：从"退化的历史"预测"还能用几年"

① 序列重建：把截面变成时间轴

对每栋烤房、每个部件，逐年计算退化分 Lᵢ(t)： Lᵢ(t) = CDCI_t( Δt = t − max(建成年, 最近维修完工年) ) t = 建成年…2026 有维修台账且 end_date 非空的那一年 → Δt 重置（回春） 整栋健康分序列 H(t) = 0.80·P_norm(t) + 0.10·M + 0.10·E 得到 时间序列样本 → 用于训练

用机理曲线"重建历史"是刻意为之：烤房没有 20 年的逐日传感器，但机理曲线给出了可信的年退化骨架，维修台账给出"回春点"，两相合成即有真量、又符合业务。这叫 机理-数据混合式时序，比纯随机的历史数据更稳。

② 网络结构与输入输出

输入窗口（滑窗长度 W=6 年，特征 6~12 维）： X_t = [H(t), 四部位分(t), 各部件剩余年限(t), 维修次数(t), 使用状态] 网络： LSTM(64) → Dropout(0.2) → LSTM(32) → Dense(1) 输出： 未来健康分 Ĥ(t+1 … t+k)，k=3~5 年 寿命外推： RUL_lstm = 从当前分降到失效阈值40分的年数

③ 融合机理寿命（不推翻原公式）

RUL_final = clamp( 0.35 × RUL_lstm + 0.65 × RUL_基 , 0, 15 ) 一致度 = 1 − |RUL_lstm − RUL_基| / 15 // 一致性体检 两者相差 > 3 年 → 标记 "ML 分歧，请人工复核"

α=0.35：机理占大头、稳；LSTM 提供"随历史波动的细粒度修正"，又不越权。健康分每季度重跑一次，序列随之刷新，寿命随之更新。

引擎 B 随机森林预警分类：从"阈值切一刀"到"模型学出来的四档判断"

① 标签怎么来（一键标注，不用人工标）

用现有机理寿命规则直接生成四档标签： RUL > 7 → 正常 4 < RUL ≤ 7 → 需关注 0 < RUL ≤ 4 → 建议维修 RUL ≤ 0 → 紧急维修 Label_i 由此生成 → 训练时的"标准答案"

不必请专家一条条标注，机理规则自动出标签，标注成本为零且口径与页面一致。

② 模型与输出

随机森林分类器： 500 棵树 · 每棵随机抽特征子集（√n）· 最多深度 12 输入 X_i（见特征工程，含 H / RUL_基 / 风险缺口 / 维修统计 / 村级 V·P·N） 输出： ① 预警等级（四档，与页面阈值同套四级） ② 各类别概率 P(紧急维修)=0.82 → 置信度高 ③ 特征重要性排序 → "为什么给它这个预警"

③ 与机理阈值互验

结果对齐策略： 随机森林等级 == 机理阈值等级 → 高可信，直接展示 不一致 → 以机理为准展示，但弹橙色提示："ML 建议上调/下调，请人工复核" 概率 P < 0.6 的样本 → 一律转人工卡片"待确认"

随机森林带来的增值：不是"改判"，而是 自动批量判断 + 给出置信度 + 给出归因。2442 栋烤房，人工看不完，模型先筛出高概率紧急维修的 Top 名单，维修队据此派工。

第六步 特征工程总表：喂给 LSTM 与随机森林的"料"

特征组维度来源进哪个引擎
机理输出H、RUL_基、风险缺口 Top3、短板部件剩余年限健康分 / 寿命模型随机森林
健康分时序H(t−5…t)、四部位分序列、部件剩余年限序列健康分模型年度回放LSTM
维修台账近 3 年维修次数、累计次数、类型分布、上次维修距今repair_records两者皆用
结构/使用容量、房龄、建成年、覆盖材料、加热器类型、use_status、dataCompleteRatioovens / kf_basedata两者皆用
村级上下文V、Hc、Lc、Dc、承载压力 P、新建需求 N、面积趋势千亩村发展指数随机森林

"数据不完整"本身也是一个特征（dataCompleteRatio=1−兜底批/总批），模型会自动学会"缺得多的烤房预警可信度要打折"，与机理兜底条款呼应。

落地 端到端工作流：从库到页面一键跑通

① 取数
ovens + kf_basedata + repair_records，0.5s 快照
② 机理层
健康分 H、寿命 RUL_基、发展指数 V（既有关口不动）
③ 特征/序列
构建 H(t) 时序 + 特征向量 X_i / X_c
④ 学习层
LSTM 输出 RUL_lstm，随机森林输出预警+概率+归因
⑤ 融合
RUL_final + 一致度 + 分歧复核 → 写库、出页面

训练与部署（真实可用，非空谈）

离线训练（一次性，Python）
数据： 2442 栋 × 按年重建序列 ≈ 上万条样本 实现： sklearn.RandomForestClassifier（分类） torch / keras 轻量 LSTM（回归） 输出： 保存 model.rf.pkl / model.lstm.pt（< 几 MB） 评估： 随机森林 5 折交叉验证， 与机理规则对比 一致性 & 混淆矩阵
在线部署（Spring Boot，Java 推理）
随机森林 → PMML（JPMML 直接 Java 加载，零依赖） LSTM → ONNX Runtime（Java 推理引擎） 两个模型文件随 jar 打包，无 GPU，CPU 毫秒级 健康分每次重算后自动更新 ovens.health_score & lifespan， 并同步写 RUL_final / warn_level / ml_note
页面呈现升级（供大屏/管理端）
  • 单栋详情：健康分 + 机理寿命 + ML 寿命三列并排，附"一致度"与"ML 分歧"提示；
  • 预警列表：随机森林四档 + 概率 + 特征归因（"主要因自控探头老化 + 近3年未修 + 村级高压"）；
  • 退化曲线图：画一条机理退化线 + 一条 LSTM 外推虚线，直观"蓝色是机理、紫色是预测"。

冷静评估 实用性边界：能落地，但要讲清楚"小样本时序"的现实

扎实可用
  • 随机森林预警：样本充足（2442 行 × 40+ 特征），分类任务成熟，指标可信，可放心上；
  • 机理曲线重建时序：每一"年"都有明确物理含义（退化+维修回春），不是造假数据；
  • 模型很小（几 MB）、推理毫秒级，普通服务器可跑，无成本门槛。
如实说明的局限
  • 烤房缺逐日/逐月传感器，LSTM 用的是"年粒度重建设列"，精细预测能力有上限——定位为"趋势增强"而非"精准到日"；
  • 若未来接入更多时间点数据（每年一次巡检或温湿度 IoT），LSTM 精度会显著上升；
  • 绝不能在评审时号称"千万级时序大数据"，会失真；正确话术是"机理-数据混合、轻量落地、可成长"。见《讲解》文档。
